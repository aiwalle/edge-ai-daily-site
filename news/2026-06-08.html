2. 【腾讯混元 HY-1.8B-2Bit：业界首个产业级 2Bit 端侧模型，存储仅 600MB，天玑 9500 首字时延加速 1.5-2×】

  • 评分：A/3 · I/4 · S=10 · P1 · 价值类型：成本优化
  • 来源：腾讯混元 / 雷峰网 / IT之家 | 雷峰网：首个产业级 2Bit 量化突破 · IT之家：0.3B 端侧模型详情 · ai-bot.cn：模型介绍 | 2026年6月

内容总结（~140 字）： 腾讯混元正式开源 HY-1.8B-2Bit，定位"面向消费级硬件的产业级端侧量化模型"。核心工程数据：① 极致压缩——原始 1.8B 参数经 2Bit 量化感知训练（QAT）后等效参数量约 0.3B，存储仅 600MB（Q4 约 1.1GB，降幅 45%）；② 量化创新：采用"数据优化 + 弹性拉伸量化 + 训练策略三重创新"，精度保留显著优于传统 PTQ 2Bit 方案；③ 实测加速：MacBook M4 首字时延 3-8× 加速（vs BF16 原始精度），生成速度 ≥2× 稳定加速；天玑 9500 对比 Q4 格式，首字时延 1.5-2×，生成速度约 1.5×；④ 部署格式：gguf-int2 与 BF16 伪量化权重均已开源，Arm SME2（天玑 9500 / 部分 Cortex-X5 设备）适配完成，llama.cpp 路径可直接加载；⑤ 腾讯称这是业界首个通过 QAT 达到产业部署门槛的 2Bit 端侧模型——此前 2Bit PTQ 精度损失过大，QAT 才实现突破。

业务价值与适配性： 可以让我们在广告端侧模型压缩中做到：参考腾讯的 QAT + 弹性拉伸量化路线，将轻量 CTR/意图识别模型从 INT4 进一步压缩至 2Bit——相比 Q4 额外减少 45% 存储，使广告模型可部署设备范围从 6GB+ RAM 扩展至 3-4GB 中端机（国内 Android 主流机型覆盖率显著提升）。适配性：中期可借鉴方法论——QAT 路线需重新训练，短期可先在 Arm SME2 设备测试 HY-1.8B-2Bit 的推理延迟作为目标基准；长期建议将 2Bit QAT 纳入广告模型压缩路线图研究。

3. 【ExecuTorch arXiv 2605.08195：Meta 亿级 DAU 量产实证——Instagram SqueezeSAM 端侧加速后 DAU 上升，50KB 运行时支撑 4 大 App】

  • 评分：A/3 · I/4 · S=10 · P1 · 价值类型：成本优化 / 新能力探索
  • 来源：Meta AI Research / arXiv | arxiv.org/abs/2605.08195 | 2026-05-05

内容总结（~140 字）： Meta AI 于 5 月 5 日在 arXiv 发布 ExecuTorch 官方技术论文，首次公开亿级 DAU 规模的端侧量产数据。关键工程信息：① 量产覆盖范围：ExecuTorch 已部署在 Instagram、WhatsApp、Messenger、Facebook 四大 App 端侧推理路径；② Instagram Cutouts（SqueezeSAM）——轻量版 Segment Anything Model 通过 ExecuTorch 替代原推理栈后，因推理速度提升导致 DAU 显著增长（端侧性能直接驱动用户活跃度的最强工业证明）；③ 运行时规格：50KB 基础运行时，12+ 硬件后端（Qualcomm NPU、Apple ANE、MediaTek APU、Arm NN、Vulkan、CoreML 等）；④ 测试设备基准：Samsung Galaxy S25 Ultra（Snapdragon 8 Elite，16GB RAM）与 Google Pixel 9 Pro XL（Tensor G4，16GB RAM）——2026 年 Android 旗舰基准机型；⑤ 80%+ HuggingFace 热门端侧 LLM 开箱即用；论文由 Meta AI Research（含 Vikas Chandra）联合撰写。

业务价值与适配性： 可以让我们在广告端侧推理栈决策中做到：① 以 ExecuTorch 为 Android + iOS 双平台量产推理栈的优选方案——Meta 社交 App 的规模验证消除了"量产可靠性"顾虑，比任何内部 PoC 更有说服力；② SqueezeSAM → DAU 提升的直接关联是立项广告端侧推理优化的最强 ROI 论证：端侧延迟降低→广告响应速度提升→点击率/留存率改善的链路已有工业实证。适配性：可直接应用——建议评估将广告侧 CTR 轻量模型的 Android NPU 推理路径从 ONNX Runtime Mobile 迁移至 ExecuTorch（PyTorch 训练管线直接导出，改造成本低）。

4. 【Edge LLM Runtime Stack 2026：7 大框架全景对比，选错运行时损失 3× 吞吐，明确各场景最优选择】

  • 评分：A/2 · I/2 · S=6 · P2 · 价值类型：成本优化
  • 来源：Edge AI Stack | The Edge LLM Runtime Stack 2026 | 2026

内容总结（~120 字）： 行业技术博客发布 2026 年边缘 LLM 推理框架横评，覆盖 7 大运行时：llama.cpp / Ollama / TensorRT Edge-LLM / ExecuTorch / vLLM / MLX / LiteRT-LM。核心结论与选型指南：① 选错运行时可损失 3× 以上吞吐——各框架的硬件加速路径差异巨大，不能随意互换；② llama.cpp：CPU-first、GGUF 格式，跨平台可移植性最强，适合"兼容性优先"场景；③ ExecuTorch：PyTorch 原生，50KB footprint，12+ 后端，移动端与 MCU 场景最优；④ LiteRT-LM：Android NPU 加速默认路径（NNAPI / 厂商 delegate），Gemini Nano 官方生产框架；⑤ 混合栈策略：原型期 Ollama → 多并发服务端 vLLM → 离线 / 端侧 ExecuTorch / llama.cpp，是 2026 年 AI 团队推荐部署模式；⑥ Ollama 与 vLLM 设计目标均为服务器并发，不适合移动端嵌入。

业务价值与适配性： 可以让我们在端侧广告推理栈选型中做到：明确框架分工——Android 端侧推理首选 LiteRT-LM（NNAPI 直通 NPU）或 ExecuTorch（PyTorch 管线兼容）；iOS 端首选 ExecuTorch + CoreAI；避免在广告移动 SDK 内嵌入 Ollama / vLLM（设计目标是服务器）。适配性：参考决策框架——建议将"训练栈 + 硬件目标 + 并发需求"三维度框架纳入内部端侧广告模型运行时选型文档。
