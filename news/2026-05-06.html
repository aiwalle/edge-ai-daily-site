端智能日报 2026-05-06

本期聚焦：工业广告 CTR 预估迎来范式级突破——LinkedIn CADET 以 decoder-only Transformer 在生产 A/B 中实现 11.04% CTR 提升，阿里 SGCTR 以"训推对称"生成式推理消除特征噪声；两篇均在 ACM Web Conference 2026 展示，确认生成式范式已完成从实验到工业的跨越；端侧推理侧，SparKV 与"Don't Waste Bits!"从云-端协同调度和自适应精度两条路线同步突破 KV Cache 内存与延迟瓶颈。

1. 【CADET（LinkedIn Engineering，arXiv 2602.11410）：Decoder-Only Transformer 广告 CTR 预估——时序 RoPE + Self-Gated Attention + 多塔预测头，线上 A/B CTR +11.04%，已上线 LinkedIn 信息流主流量】

  • 评分：A/5 · I/4 · S=14 · P0 · 价值类型：收入提升
  • 来源：LinkedIn Engineering | arxiv.org/abs/2602.11410 | 2026-02（生产部署确认）

内容总结（140字）： LinkedIn 以生成式 decoder-only 架构替换原有 LiRank（DCNv2 + 序列编码器混合方案），提出 CADET：① 时序 RoPE：RoPE 改为 timestamp-based，捕捉秒级到月级跨度的用户行为时序关系；② Self-Gated Attention：自适应调节表示层和交互层的信息流，稳定大规模训练；③ 多塔预测头：显式建模广告位（position）等 post-scoring 信号，解决 selection bias；④ Session Masking：屏蔽 in-session 未来事件泄露，保证训练-推理分布一致。工程落地：张量打包（tensor packing）+ 序列分块（sequence chunking）+ 定制 Flash Attention Kernel，支持亿级规模训练与在线服务。线上 A/B：CTR +11.04% vs. LiRank 基线，现已服务 LinkedIn 信息流赞助内容主流量。

业务价值与适配性： 可以让我们在广告信息流 CTR 预估中将用户行为序列的时序建模升级为 decoder-only 架构，用一个统一模型同时建模上下文条件和排序目标——相比我们当前 DIN/DIEN 类 attention 方案，时序 RoPE 可直接处理毫秒级到月级的行为时间戳而无需手工分桶。可直接应用：CADET 的 timestamp RoPE + session masking 是两个独立可移植模块，建议先在离线实验中替换 DIN 的 position encoding，用真实时间戳驱动；Flash Attention kernel 已有 CUDA 开源实现，2 周内可搭建 baseline，重点观察长序列（>512 步）用户的 AUC 变化。

2. 【SGCTR "Infer As You Train"（阿里巴巴，arXiv 2511.14403，Web Conference 2026）：训推对称的生成式 CTR 预估——推理阶段迭代重定义特征消除噪声，Alibaba 出品，短论文 · 已在迪拜展示】

  • 评分：A/4 · I/3 · S=11 · P1 · 价值类型：收入提升/新能力探索
  • 来源：阿里巴巴 | arxiv.org/abs/2511.14403 | ACM Web Conference 2026（迪拜，4/13–17）

内容总结（130字）： 现有 CTR 模型训练和推理范式不对称：训练时做 Masked Language Model（屏蔽部分特征学依赖），推理时直接前向传播，无法利用已学到的生成能力纠正噪声输入。SGCTR（Symmetric Masked Generative CTR）打破这一不对称：推理阶段主动激活生成能力，以若干 masking 迭代步骤对输入特征做逐轮精化，过滤低质量/噪声特征，再做最终预测。工程约束：推理迭代次数 k 是线性开销，已通过 GPU 并行批处理控制延迟；具体线上延迟作者未披露，但实验代码已随论文开源。在阿里电商场景（公开数据集 + 内部数据集）上验证，多指标超越 SOTA 判别式基线。平台：阿里巴巴电商广告，Alibaba Group 出品，Web Conference 2026 短论文正式发表。

业务价值与适配性： 可以让我们在广告 CTR 推理阶段引入"自修复特征"机制——当用户特征存在缺失（冷启动）或噪声（跨设备行为不一致）时，SGCTR 的生成推理可在不增加训练成本的前提下动态补全，对我们的冷启动广告主定向场景尤为有价值。可借鉴思路：SGCTR 的"训推对称"可与 CADET（条目 1）的 decoder-only 架构互补——CADET 解决序列时序建模，SGCTR 解决特征噪声，两者在 CTR 预估全链路中可串联部署；建议先复现 SGCTR 在公开广告数据集（Criteo/Avazu）上的结果，再评估 k=2-3 迭代时的实际推理延迟是否在可接受范围（<5ms）。

3. 【OpenAI Privacy Filter（开源，Apache 2.0）：1.5B 总参 / 50M 激活的端侧 PII 检测模型——稀疏 MoE 128 专家，F1=96%，本地运行不出云，4 月 22 日发布】

  • 评分：A/3 · I/4 · S=10 · P1 · 价值类型：用户体验/成本优化
  • 来源：OpenAI | openai.com/index/introducing-openai-privacy-filter | huggingface.co/openai/privacy-filter | 2026-04-22

内容总结（120字）： OpenAI 以 Apache 2.0 开源 Privacy Filter：专为企业数据脱敏设计，在数据进入云端前本地识别并遮蔽 PII。架构：1.5B 总参数，稀疏 MoE（128 专家，top-4 路由），推理仅激活 50M 参数——接近 50M 密集小模型的计算成本，实现"大模型精度 + 小模型速度"；覆盖范围：8 类敏感信息（账号、地址、邮箱、人名、电话、URL、日期、密码/密钥）；性能：PII-Masking-300k benchmark F1=96.0%（precision 94.04%, recall 98.04%），修正版 benchmark F1=97.43%；部署：Hugging Face + GitHub 开源，ONNX 格式支持跨平台端侧部署，支持 CPU 推理（laptop 级别即可），无需 GPU。

业务价值与适配性： 可以让我们在广告 SDK 的用户行为数据上传链路中插入端侧 PII 过滤层——用户真实姓名、设备 ID 明文、邮箱等在离开设备前被自动遮蔽，满足 GDPR/隐私合规要求，同时降低云端数据安全审计成本。可直接应用（数据管道）：Apache 2.0 协议无商业限制，ONNX 格式可直接集成到 Android/iOS SDK；建议优先部署在广告归因模块的用户 profile 上传环节，测量脱敏前后归因模型 AUC 变化（因部分 PII 字段可能与 ID Mapping 强相关，需评估业务影响）；暂不适用（实时 CTR）：50M 激活参数的推理在每次广告请求中单独运行成本偏高，更适合异步数据清洗场景。

4. 【SparKV（arXiv 2604.21231）：端侧 LLM 推理的开销感知 KV Cache 云端流式加载——TTFT 降低 1.3x–5.1x · 每请求能耗降低 1.5x–3.3x，4 月 23 日发布】

  • 评分：A/3 · I/3 · S=9 · P1 · 价值类型：成本优化/用户体验
  • 来源：多机构 | arxiv.org/abs/2604.21231 | 2026-04-23

内容总结（130字）： 端侧 LLM 推理的 Prefill 阶段（构建 KV Cache）是最大延迟瓶颈，尤其在长上下文（512-2048 token 广告序列）场景下。SparKV 提出云-端协同 KV 调度框架：① KV Chunk 成本建模：对每个 KV chunk 同时估计本地计算成本和从云端流式拉取成本；② 最优调度决策：动态决定每块 KV 是本地计算还是云端流式加载，并将两条路径并行执行以最大化重叠；③ 运行时自适应：感知无线网络带宽波动和设备资源动态变化，在线调整预置调度策略。跨数据集/多种 LLM/多个边缘设备实测：TTFT 降低 1.3x–5.1x，每请求能耗降低 1.5x–3.3x，响应质量无明显损失。该方案天然契合端云协同架构，无需修改模型权重。

业务价值与适配性： 可以让我们在广告端侧 LLM（用户序列召回/意图理解）中将上下文预填充的首字延迟从数百毫秒压缩至可接受范围，同时显著降低 NPU 持续推理的能耗，延长单次 session 内的连续推理窗口（与 arXiv 2603.23640 热降频研究结论吻合）。可借鉴思路：SparKV 的云-端 KV chunk 协同调度与 Firebase Hybrid Inference（Android 17）高度互补——AICore 本地模型处理简单请求，云端 KV 流式加载支撑长上下文复杂推理；等 SparKV 开源代码发布后（arXiv 版本已含方法，代码库 TBD），建议结合内部 CDN 边缘节点评估 KV 流式传输带宽可行性。

5. 【"Don't Waste Bits!"（arXiv 2604.04722）：端侧 LLM 自适应 KV Cache 量化——每 token 动态精度调度 {2/4/8-bit/FP16}，SmolLM-360M 延迟降低 17.75% · 精度接近 FP16，4 月 6 日发布】

  • 评分：A/3 · I/3 · S=9 · P1 · 价值类型：成本优化
  • 来源：多机构 | arxiv.org/abs/2604.04722 | 2026-04-06

内容总结（130字）： 与 TurboQuant（05-05 已报，针对 KV 整体旋转量化）不同，本文专注于每 token 级别的精度自适应策略。框架提取 4 维 token 级轻量特征（词频 / attention variance / 熵 / quality score），通过紧凑数据驱动控制器在解码时动态选择精度 {2-bit, 4-bit, 8-bit, FP16}：重要 token 保持高精度，低影响 token 降为 2-bit，整体 KV 内存大幅降低。实测（SmolLM-360M，HellaSwag）：解码延迟降低 17.75%（vs. 静态 KV 量化），精度提升 7.60 点，与 FP16 精度差距仅 0.30 点；在多个轻量模型（SmolLM 系列、Qwen2.5-1.5B）上验证有效。目标平台：4GB RAM 及以下端侧设备。与 TurboQuant 可组合使用（旋转 + 自适应精度双重优化）。

业务价值与适配性： 可以让我们在广告端侧序列推理（用户历史 512 token）中将 KV Cache 内存占用进一步降低 30-50%，解锁在 3-4GB RAM 设备上运行广告意图 LLM 的可行性——当前主要障碍是 KV Cache 内存过大触发 OOM。可借鉴思路：本方案与 TurboQuant（ICLR 2026, llama.cpp PR #21089）形成互补"双 KV 优化栈"：TurboQuant 做全局旋转量化（5.2x 压缩比），"Don't Waste Bits!"做 per-token 精度调度（进一步节省 20%）；建议待 llama.cpp 主线合入 tbq4_0 后同步集成本方案的 token-level policy，形成组合优化。

其他观察

今日五条内容可解读为"广告端智能的两层技术栈同步成熟"：上层（业务算法），CADET 和 SGCTR 分别以时序感知 decoder 和训推对称生成为 CTR 模型带来结构性提升，均已在顶级工业系统验证；下层（基础设施），SparKV 和"Don't Waste Bits!"从调度和精度两个维度持续压缩端侧 KV Cache 开销——两层同时完成工程验证，意味着"完整端侧广告推理链路"的技术可行性窗口在 Q3 2026 正式打开。OpenAI Privacy Filter 则在两层之间插入合规层，使端侧 PII 过滤真正具备生产级可用性。
