端智能日报 2026-06-29

本期聚焦：双线工程进展——Google LiteRT-LM Gemma 4 MTP 2.2x 加速（52-76 tok/s）提供端侧 LLM 广告推理的 Android 主路径；真实设备持续推理基准（arXiv 2603.23640）揭示热管理才是当前最硬约束，iPhone 16 Pro 2 轮迭代内丢失 50% 吞吐。IJCAI-ECAI 2026 联邦推荐综述同步提供端侧隐私用户建模完整知识框架，三者共构 H2 2026 广告端侧化落地参考坐标。

1. 【联邦 Foundation Model 推荐综述（IJCAI-ECAI 2026 Survey Track）：端侧隐私用户建模 + 基础模型协同的完整知识框架——FedFM 解锁"数据不出设备 + 大模型语义能力"双赢路径（arXiv 2506.11563）】

  • 评分：A/4 · I/3 · S=11 · P1 · 价值类型：用户体验 / 新能力探索
  • 来源：多机构合作 / IJCAI-ECAI 2026 Survey Track | arXiv 2506.11563 | 2025-06 投稿，2026 年接收（v2 最新修订）

内容总结（约 140 字）： 本文系统综述"个性化联邦基础模型（FedFM）在隐私保护推荐"方向，填补联邦学习 × 推荐系统 × LLM 三角交叉的知识空白——核心矛盾：基础模型需要海量用户行为数据驱动，联邦学习要求原始数据永不离端，调和两者需要轻量化端侧适配器 + 跨设备联邦聚合的精细协同。综述归纳关键发现：单知识轻量模型内存占用低但知识替换质量差；双知识高性能模型精度强但内存太大难以在端侧部署——形成直接指导当前端侧广告用户建模的权衡框架。工程信息：端侧适配器（LoRA / Prompt Tuning 等）+ 联邦聚合服务器；无具体设备延迟数字，以隐私保障 + 个性化精度为主要指标。即将在 IJCAI-ECAI 2026（预计 2026 年 8 月）正式发表。

业务价值与适配性： 可以让我们在端侧广告用户建模中做到：以联邦 LoRA 方式在用户设备上对基础模型（Qwen/MiniCPM 等）进行轻量个性化微调，生成每个用户私有的意图向量，再通过安全聚合上云更新全局 CTR/CVR 模型——实现"用户行为数据完全端侧，模型迭代能力保留云侧"。可借鉴思路：综述的双知识 vs 单知识权衡分析可直接用于端侧广告 embedding 设计的内存预算决策（当前主流旗舰手机 DRAM 8-12GB，能否承载双知识适配器是关键约束）。

2. 【Google LiteRT-LM Gemma 4 MTP：端侧 LLM 推理 2.2x 加速——Multi-Token Prediction 投产，Android GPU 52 tok/s、iOS Metal 56 tok/s、WebGPU 76 tok/s，Gemini Nano 生产路径正式开源】

  • 评分：A/3 · I/4 · S=10 · P0 · 价值类型：成本优化 / 用户体验
  • 来源：Google AI Edge / InfoQ | InfoQ 报道 · Google Developers Blog · GitHub | 2026-05（v0.11.0）/ 2026-06（MTP 报道）

内容总结（约 140 字）： Google AI Edge 正式发布 LiteRT-LM，这是驱动 Gemini Nano 在 Chrome、ChromeOS、Pixel Watch 及 Google AI Edge Gallery 量产运行的同款开源推理框架。关键更新：新增对 Gemma 4 系列 Multi-Token Prediction（MTP）的原生支持，通过推测解码变体将解码速度最高提升 2.2x。性能基准：Gemma 4 E2B（有效参数 2B 的 MatFormer 版），Android OpenCL GPU 52 tok/s，iOS Metal 56 tok/s，MacBook Pro WebGPU 76 tok/s；更高端的 E4B 版（有效参数 4B）同样支持但速度更低。技术栈：XNNPACK（CPU）+ MLDrift（下一代 GPU 引擎，支持 OpenCL/OpenGL/Metal/WebGPU）+ 可选 QNN NPU backend；编排层通过优化管道避免 CPU/GPU 数据转移开销。工程信息：生产级、开源（Apache 2.0）；v0.11.0 版本，CLI 和移动端 SDK 均可下载。

业务价值与适配性： 可以让我们在 Android 广告端侧推理中做到：以 LiteRT-LM 作为 Gemma 4 E2B/E4B 的推理底座，快速搭建广告意图理解（搜索词 → 广告类目映射）和轻量素材理解模块，并通过 MTP 将 token 生成延迟降低 2.2x——在 50ms 竞价窗口内完成更多语义处理步骤。可直接应用（端侧推理执行层）：LiteRT-LM 已是 Google 产品生产验证路径，开源且文档完整；建议 1-2 周内在测试机上运行 Gemma 4 E2B + 广告意图分类任务，以 52 tok/s baseline 为起点评估实际广告场景 P99 延迟。P0 核心理由：开源可用、文档齐全、有真实 tok/s 数据，是当前 Android 广告端侧 LLM 路径中最低试错成本的选择。

3. 【MediaTek NPU + LiteRT NeuroPilot Accelerator：数亿 Android 中端机获得生产级 NPU 加速——Gemma 3 全系原生支持，零拷贝 AHardwareBuffer，100× CPU 推理速度】

  • 评分：A/3 · I/3 · S=9 · P1 · 价值类型：新能力探索
  • 来源：Google AI Edge / MediaTek | Google Developers Blog · MediaTek Tek Talk

内容总结（约 130 字）： Google 与 MediaTek 联合宣布 LiteRT NeuroPilot Accelerator，TFLite NeuroPilot delegate 的全新一代替代方案，面向 MediaTek APU（天玑系列 SoC）的深度 NPU 加速。核心改进：① 统一开发工作流——开发者通过标准 LiteRT API 无需感知硬件差异即可调用 MediaTek NPU；② Gemma 3 全系原生支持（270M、1B、multimodal 3n E2B）；③ Native Hardware Buffer Interoperability——零拷贝 AHardwareBuffer 数据传递，消除 CPU/NPU 数据搬运开销；④ 性能：相较 CPU 高达 100x，相较 GPU 高达 10x。覆盖范围：天玑系列广泛搭载于中端 Android 机（国内市场份额约 40%），意味着端侧 AI 能力不再只限旗舰机。工程信息：已面向所有开发者开放，生产就绪。

业务价值与适配性： 可以让我们在广告 SDK 的覆盖率中做到：以 LiteRT NeuroPilot Accelerator 覆盖天玑设备（国内大量中端机），将端侧广告推理的实际触达用户比例从当前高端 Snapdragon 专属提升至更广泛的 Android 生态。可借鉴思路：LiteRT API 统一旗舰机（Snapdragon+QNN）与中端机（MediaTek+NeuroPilot）的调用层，意味着广告 SDK 可以写一套代码适配两条 NPU 路径；结合 LiteRT-LM（上一条），形成从中端到高端 Android 机的完整端侧 LLM 覆盖链。

4. 【arXiv 2603.23640：端侧 LLM 推理的真正天花板——热管理 > 算力峰值，iPhone 16 Pro 两轮内损失 50% 吞吐，S24 Ultra OS 强制终止 GPU 推理】

  • 评分：A/3 · I/3 · S=9 · P1 · 价值类型：成本优化 / 工程实践
  • 来源：学术团队 | arXiv 2603.23640 | 2026-03-24

内容总结（约 140 字）： 论文对四个平台进行了面向"持续推理负载"的系统基准测试，评估 Qwen 2.5 1.5B（4-bit 量化）在固定 258-token prompt 下持续 20 次热推理的吞吐量、延迟、功耗与热行为——刻意模拟"广告场景下 LLM 连续服务请求"这类 always-on 负载。关键发现（直接影响广告工程规划）：① iPhone 16 Pro：连续推理仅 2 轮后因热降频损失近 50% 吞吐量；② Samsung Galaxy S24 Ultra：OS 强制施加 GPU 频率下限，在持续高负载下直接终止推理；③ RTX 4050 (笔记本)：受限于电池功耗上限；④ Hailo-10H NPU：受限于板载内存带宽。核心结论："对于移动设备，热管理已取代算力峰值，成为持续推理的首要约束。"工程信息：真实设备 benchmark，Qwen 2.5 1.5B Q4，持续负载场景。

业务价值与适配性： 可以让我们在广告端侧 LLM 工程规划中做到：在 SDK 设计阶段引入"热感知推理调度"——当检测到设备温度升高时主动降低推理频率或切换到更轻量模型，防止 S24 Ultra 类硬终止场景导致广告请求超时。可借鉴思路：这个基准强烈支持 EnerInfer（见 2026-06-28 简报）的"配置松弛空间"框架——广告后台请求（非实时竞价路径）主动降频能有效规避热降频引发的 P99 延迟波动，两者形成互补的工程解决方案。

5. 【MiniCPM5-1B（面壁智能 / 清华）：1B 参数级 SOTA 端侧 LLM——FlagOS 多芯片统一调度，4-5 款 AI 芯片极短时间完成适配，Hybrid Thinking 模式端侧可用】

  • 评分：A/3 · I/3 · S=9 · P2 · 价值类型：新能力探索
  • 来源：OpenBMB / 面壁智能（清华大学）| GitHub OpenBMB/MiniCPM · HuggingFace openbmb/MiniCPM5-1B | 2026-05（中文源：OpenBMB GitHub 中文文档）

内容总结（约 130 字）： 面壁智能（OpenBMB，清华大学主导）发布 MiniCPM5-1B，1B 参数类目新 SOTA，专为本地部署、边缘 AI 和端侧 Agent 优化。核心亮点：① Hybrid Reasoning——通过 <think> 模板可切换快速回答 vs 深度推理两种模式，同一 checkpoint 兼容，适合广告意图理解（快速）和复杂素材分析（深度）场景；② 多芯片适配——通过 FlagOS（智源研究院统一多芯片 AI 软件栈）仅用极短时间完成对 4-5 款不同 AI 芯片的适配并发布 FlagRelease，覆盖国产芯片生态；③ 部署路径丰富：llama.cpp（CPU/Edge/Apple Silicon）、Apple MLX、vLLM、SGLang，GGUF 格式直接可用。关键指标：Agent 工具调用和代码生成优势最显著，超越同参数级对手。工程信息：已量产，多生态均有官方 cookbook。

业务价值与适配性： 可以让我们在国产 AI 芯片生态的广告端侧推理中做到：以 MiniCPM5-1B + FlagOS 快速完成国产芯片（麒麟 / 天玑 / 自研 NPU）上的广告意图识别模块验证，绕过 Qualcomm QNN 生态限制，打通国内 Android 碎片化芯片的端侧覆盖。暂不适用于高质量广告素材理解（1B 参数语义能力不足），但其 Hybrid Thinking 模式可在意图识别（快速）和策略解释（深度）两条路径间动态切换，契合广告 SDK 的低延迟主路径 + 偶发深度分析双需求架构。
