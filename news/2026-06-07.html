2. 【端侧 LLM 推理热节流实证：iPhone 16 Pro 持续推理掉速 44%，热管理超越 TOPS 成真实瓶颈（arXiv 2603.23640）】

  • 评分：A/3 · I/3 · S=9 · P1 · 价值类型：成本优化 / 用户体验
  • 来源：arXiv | arxiv.org/abs/2603.23640 | 2026-03

内容总结（~150 字）： 来自 2026 年 3 月的基准测试论文，近期在工程社区持续发酵。研究对 Qwen 2.5 1.5B（INT4 量化）在四类设备上进行 20 轮持续推理实测，关键发现如下：① iPhone 16 Pro——峰值 40.35 tok/s，但热节流在第 2 次推理后即触发，65% 的测试时间处于降速状态，最终稳定在 22.56 tok/s（掉速 44%）；② Samsung Galaxy S24 Ultra——OS 强制执行 GPU 频率下限（OS-enforced freq floor），极端情况会直接终止推理；③ Hailo-10H NPU（Raspberry Pi 5 附加板）——吞吐稳定性 CV 仅 0.04%（比任何其他平台低 2 个数量级），270 mJ/token，表现最稳定；④ NVIDIA RTX 4050 笔记本——受电池功率上限约束，与 Hailo-10H 能效相近（259 vs 270 mJ/token）但吞吐差 19×。结论：高 TOPS 不等于高持续吞吐，移动端 LLM 的真实瓶颈是热管理，而非算力。

业务价值与适配性： 可以让我们在端侧广告推理 SLA 设计中做到：① 将设备端推理吞吐 SLA 基准从峰值改为持续值——iPhone 设计目标应基于 22 tok/s 而非 40 tok/s，避免上线后性能劣化导致广告展示延迟；② 为端侧 CTR 推理设定热状态 SLA（连续 5+ 次推理后的延迟上限），并在 SDK 层加入热状态检测逻辑，动态降级到云端推理。适配性：可直接指导工程规划——建议将此论文的持续推理 profiling 方法引入内部端侧模型压测 CI 流程，覆盖"冷启动"和"连续重复推理"两种场景。

3. 【Chrome for Android Gemini AI 自动浏览（6月底美国首发）：浏览器内用户意图执行首次端侧量产】

  • 评分：A/3 · I/3 · S=9 · P1 · 价值类型：新能力探索
  • 来源：Google Chrome Blog | Gemini in Chrome with auto browse comes to Android | 2026-06

内容总结（~130 字）： Google 宣布将 Gemini AI 能力引入 Chrome for Android，6月底面向美国用户开始灰度，覆盖条件：Android 12+ / 4GB RAM 以上设备（无需旗舰芯片，显著扩大覆盖面）。核心功能：① Auto Browse（自动浏览）——用户以自然语言描述目标（如"帮我预订最近的停车位""更新我的订单地址"），Gemini 在浏览器内自主执行多步网页任务，首次将"意图→操作"闭环能力下沉至手机浏览器层；② Article Summarizer——当前页文章即时摘要，端侧处理，零云端请求；③ Image Customizer / Task Manager——页面内图片编辑与任务追踪。底层推理框架为 LiteRT-LM（即 6月3日报道的 Gemini Nano 生产矩阵），确保端侧推理延迟 <200ms。

业务价值与适配性： 可以让我们在 Web 广告场景中做到：① 利用 Chrome Gemini 的用户意图感知能力为 Web 广告提供更精准的页面级上下文信号——用户"让 Gemini 预订停车位"这一动作本身就是强意图信号，可接入浏览器端广告竞价策略；② Auto Browse 的多步操作链路可与广告落地页深度绑定，探索"AI 辅助转化"新交互模式（类似导购 Agent）。适配性：中期关注——6月底仅限美国，功能对应广告侧的 API 尚待 Chrome 开放；建议今天即注册 Chrome Canary 内测资格，提前熟悉 Prompt API 与 Auto Browse 的能力边界。

4. 【2026 移动端 AI 推理范式转移：端侧作为默认选项成行业共识，30ms vs 800ms 分水岭确立】

  • 评分：A/4 · I/2 · S=10 · P1 · 价值类型：成本优化 / 用户体验
  • 来源：SEM Nexus / Edge AI and Vision Alliance / On-Device LLMs 2026 综合 | SEM Nexus：On-Device AI in Mobile Privacy-First Pattern · Edge AI Vision Alliance | 2026

内容总结（~130 字）： 多方 2026 年行业综述交叉印证同一结论：端侧推理在移动 AI 应用中已从"可选项"切换为"默认选项"。关键技术转折点：① 性能分水岭确立——情感分类/意图识别等轻量 NLP 任务，端侧推理约 30ms（iPhone 15+/近两年 Android 旗舰，30+ TOPS），而服务端 API 往返含网络 RTT 约 800ms，差距超 25×；② 隐私监管倒逼——App Tracking Transparency（ATT）、GDPR 严格执行、Privacy Sandbox 落地，使"用户行为数据上云"的合规成本持续攀升，端侧推理本身即满足"数据不离端"要求；③ 80% 推理本地化：2026 年预测全球 AI 推理中约 80% 将在设备端完成；④ 推理框架成熟——ExecuTorch 1.0 GA + LiteRT 2.1 生产毕业 + CoreML/Core AI 同时演进，双平台 INT4 量化量产路径均已打通。

业务价值与适配性： 可以让我们在广告系统架构决策中做到：① 以"端侧优先，云端兜底"作为 2026-2027 广告意图识别 / 实时 CTR 推理的架构原则——30ms 端侧延迟远低于任何云端实时竞价链路的容忍上限（通常 <100ms），意味着端侧不仅是隐私方案，还是性能优化方案；② 将设备 NPU 算力（TOPS）从"广告侧可选加分项"升级为 SDK 能力分级的强依赖——建议在 SDK 设备能力矩阵中新增"端侧推理等级"维度（NPU ≥ 10 TOPS = 全功能，CPU 降级 = 简化特征），对应差异化广告策略。适配性：可直接应用于架构规划——将此框架纳入下一版 SDK 技术设计文档，作为端侧 AI 能力分层的依据。

其他观察

今日端侧 AI 生态整体处于"WWDC 前一天"的静默期：所有开发者视线集中在明日 keynote。arXiv 热节流实测和 Chrome Auto Browse 代表了两个维度的"工程现实"——一个揭示了当前端侧推理的硬性约束（热管理），一个展示了下一个 UI 范式（浏览器原生 AI Agent）。两者合并阅读的启示：端侧广告推理 SDK 的下一个设计挑战，不是"能不能跑模型"，而是"连续跑 10 次之后还能不能稳定在 SLA 内"，以及"当用户已经有浏览器原生 AI Agent 时，广告如何接入这一新交互层"。
